# Optimizer README

## 1. Назначение

Optimizer - часть Multi-Agent System, которая получает:

* текущее состояние процесса;
* допустимые границы управляемых параметров;
* результаты оценки качества;
* оценку энергетической стоимости сценариев.

На выходе формируется:

1. набор допустимых сценариев;
2. Pareto-front по качеству и энергозатратам;
3. выбранный сценарий;
4. конкретные изменения технологических параметров для оператора.

Текущая реализация является прототипом и работает через CSV-файлы.

# 4. Входные данные

## 4.1 `base_state.csv`

Содержит текущее состояние процесса.

Используется как базовая точка для генерации сценариев.

Для каждого управляемого параметра текущее значение должно находиться внутри заданных границ.

Если параметр отсутствует в `base_state.csv` или его текущее значение выходит за пределы:

```text
lower_bound <= current <= upper_bound
```

генератор завершает работу с ошибкой.

---

## 4.2 `controllable_bounds.csv`

Определяет управляемые параметры:

```text
parameter,lower_bound,upper_bound
```

Например:

```text
parameter,lower_bound,upper_bound
hdt_T01,320,360
hdt_P01,20,30
hdt_F01,100,140
```

Эти границы используются именно Optimizer'ом.

Исторические min/max сами по себе не являются технологическими ограничениями.

# 5. `scenario_generator.py`

## Назначение

Создаёт набор кандидатов, изменяя управляемые параметры относительно текущего состояния.

Текущие настройки:

```python
N_STEPS = 5
STEP_FRACTION = 0.025
```

То есть шаг равен 2.5% полного допустимого диапазона параметра.

Для каждого параметра рассматриваются значения:

```text
current - 5*step
...
current - step
current
current + step
...
current + 5*step
```

Всего потенциально 11 значений на параметр.

После этого строится декартово произведение всех значений:

```python
itertools.product(*parameter_values)
```

Каждой комбинации присваивается `candidate_id`.

### Важное ограничение

Количество сценариев растёт экспоненциально:

```text
11 параметров → 11^11 = 285 311 670 611 сценариев
```

Поэтому полный grid подходит только для небольшого количества управляемых параметров.

При увеличении числа параметров потребуется перейти на:

* ограниченный grid;
* random sampling;
* Latin Hypercube;
* Bayesian optimization;
* evolutionary optimization;
* либо последовательный поиск вокруг текущего режима.

На текущем этапе используется полный grid как простой и воспроизводимый MVP.

# 6. `quality_evaluator.py`

## Назначение

Передаёт каждый сценарий в Quality Agent и получает прогноз качества.

Поток:

```text
scenarios.csv
      ↓
Quality Agent
      ↓
predicted_sulfur_mg_kg
      ↓
quality_feasible
```

Минимально необходимые результаты:

```text
candidate_id
predicted_sulfur_mg_kg
sulfur_limit_mg_kg
limit_exceeded
quality_feasible
```

`quality_feasible = True` означает, что сценарий прошёл проверку качества.

Optimizer не пытается компенсировать нарушение качества экономической выгодой.

---

# 7. `energy_proxy.py`

## Назначение

Рассчитывает условную энергетическую стоимость сценария.

Текущая версия использует proxy-модель, а не реальные данные энергопотребления.

Результат:

```text
candidate_id
energy_proxy_eu_h
```

Энергия является вторым оптимизируемым критерием.

Важно:

> `energy_proxy_eu_h` не следует интерпретировать как фактическое промышленное энергопотребление.

Это временная модель для демонстрации и разработки Optimizer.

Для production-версии её следует заменить:

* фактическим энергопотреблением;
* либо физической/регрессионной моделью;
* либо другим подтверждённым экономическим proxy.

---

# 8. `pareto_optimizer.py`

## Назначение

Объединяет результаты Quality Agent и Energy Proxy и ищет компромисс между:

1. качеством продукта;
2. энергетической стоимостью.

Оба критерия минимизируются:

```text
predicted_sulfur_mg_kg
energy_proxy_eu_h
```

---

## 8.1 Фильтрация качества

Сначала рассматриваются только сценарии:

```python
quality_feasible == True
```

Сценарии, нарушающие жёсткое ограничение качества, не участвуют в Pareto-оптимизации.

Если допустимых сценариев нет, Optimizer завершает работу с ошибкой.

---

## 8.2 Поиск Pareto-front

Предыдущая реализация перебирала каждый сценарий относительно всех остальных.

Текущая реализация использует алгоритм для двух критериев:

```text
1. сортировка по energy_proxy_eu_h
2. проход слева направо
3. отслеживание минимальной серы
```

Сложность:

```text
O(N log N)
```

вместо:

```text
O(N²)
```

за счёт сортировки.

## Для ускорения используются NumPy-массивы и `np.minimum.accumulate()`.

## 8.3 Удаление дубликатов

Перед расчётом Pareto удаляются сценарии с одинаковыми:

```text
predicted_sulfur_mg_kg
energy_proxy_eu_h
```

Для Pareto такие сценарии эквивалентны.

---

# 9. Выбор одного сценария

Pareto-front обычно содержит несколько допустимых вариантов.

Optimizer должен выбрать один.

Текущий метод:

```text
1. Нормализовать sulfur → [0, 1]
2. Нормализовать energy → [0, 1]
3. Рассчитать расстояние до точки (0, 0)
4. Выбрать минимальное расстояние
```

Формула:

```text
distance =
sqrt(
    sulfur_normalized² +
    energy_normalized²
)
```

`(0, 0)` соответствует условному идеальному сценарию:

```text
минимальная сера
+
минимальная энергия
```

Расчёт выполняется через NumPy.

### Важное замечание

Это не означает, что такой сценарий является «оптимальным вообще».

Это конкретное правило выбора компромисса с равным вкладом двух нормализованных критериев.

В дальнейшем его можно заменить на бизнес-/технологическое правило.

# 11. `show_action.py`

Этот скрипт превращает выбранный сценарий в понятное действие.

Он сравнивает:

```text
текущее значение
        ↓
рекомендованное значение
```

и показывает только изменяемые параметры.

Пример:

```text
hdt_T01: 340.0 → 345.0 (Δ +5.0)
hdt_P01: 25.0 → 26.0 (Δ +1.0)
```

После этого выводятся:

```text
predicted sulfur
energy proxy
```

То есть:

```text
Optimizer
    ↓
selected_scenario.csv
    ↓
show_action.py
    ↓
рекомендация оператору
```

# 13. Интеграция в MAS

В конечной системе эти скрипты не должны оставаться отдельными CLI-скриптами.

Нужен один `Optimizer Agent`, который получает состояние от MAS.

Логически:

```text
                    ┌─────────────────┐
                    │ Reliability     │
                    │ Agent           │
                    └────────┬────────┘
                             │
                       valid state
                             │
                             ▼
                    ┌─────────────────┐
                    │ Optimizer Agent │
                    └────────┬────────┘
                             │
              ┌──────────────┼──────────────┐
              ▼              ▼              ▼
		    ┌─────────────┐
         Scenario   │   Quality   │     Energy
         Generator  │   Agent     │     Proxy
		    └────────┬────┘
              │              │              │
              └──────────────┼──────────────┘
                             ▼
                       Pareto search
                             │
                             ▼
                      Selected scenario
                             │
                             ▼
                        Recommendation
```

# 14. Роль Reliability Agent

Optimizer не должен самостоятельно принимать решение на основании потенциально плохих данных.

Перед запуском оптимизации Reliability Agent должен проверить:

* наличие обязательных тегов;
* свежесть данных;
* пропуски;
* аномальные значения;
* согласованность данных;
* возможность безопасного проведения расчёта.

Если состояние ненадёжно:

```text
Reliability Agent
       ↓
state_invalid
       ↓
Optimizer НЕ запускается
```

Если состояние корректно:

```text
Reliability Agent
       ↓
state_valid
       ↓
Optimizer запускается
```

# 15. Текущие ограничения

## 15.1 Scenario Generator

Полный Cartesian Grid быстро становится огромным.

При 11 значениях на параметр:

```text
N параметров → 11^N сценариев
```

Поэтому масштабирование количества управляемых параметров является текущим ограничением.

---

## 15.2 Energy Proxy

Текущий energy proxy не является физической моделью энергопотребления.

Его нужно заменить или калибровать на реальные данные.

---

## 15.3 Quality Agent

Если Quality Agent выдаёт практически одинаковый прогноз серы для разных сценариев, Pareto-front фактически определяется только Energy Proxy.

Это необходимо проверить до дальнейшего усложнения Optimizer.

---

## 15.4 Выбор сценария

Текущее правило:

```text
равный вклад:
качество + энергия
```

не обязательно соответствует реальной производственной политике.

В production-системе правило выбора должно быть согласовано с технологическими приоритетами.

---

## 15.5 Жёсткие ограничения

Нарушение технологического ограничения не должно компенсироваться:

```text
экономией энергии
+
увеличением производительности
```

То есть сначала:

```text
SAFETY / QUALITY / TECHNOLOGY
```

и только среди допустимых вариантов:

```text
ECONOMICS / ENERGY
```
