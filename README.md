# Обработка данных (ЛИМС / ПАК / формулы качества)

Три скрипта для подготовки данных к обучению агентов:

- `lims_parser.py` — разбирает лабораторные анализы (ЛИМС)
- `pak_parser.py` — разбирает поточный анализатор качества (ПАК)
- `quality_formulas.py` — считает показатели качества по тегам КИП
  (формулы ВАК)

Первые два просто приводят сырые Excel-файлы к удобному формату
(одна строка = одно измерение). Третий - не про формат, а про расчет:
вычисляет **новые** величины (T90, T50, CloudPoint, CFPP) из тегов
КИП, которых в исходном CSV нет вообще.

## Установка

```bash
python3 -m venv venv
source venv/bin/activate   # Windows: venv\Scripts\Activate.ps1
pip install -r requirements.txt
```

## Куда класть датасеты

Исходные файлы нужно положить в папку `data/` рядом со скриптами:
```
data/
  ЛИМСы ... .xlsx
  Выгрузка_ПАК ... .xlsx
  242000_tags.csv
```
`quality_formulas.py` датасета не требует — считает по строке тегов,
которую ему передают (см. ниже).

## lims_parser.py

Разбирает `ЛИМСы ... .xlsx` из широкого формата (даты и значения парами
колонок, сгруппированные по установке/точке отбора/продукту) в длинную
таблицу.

Результат — DataFrame с колонками: `timestamp`, `sampling_point`
(например, `"АВТ:1"`), `product`, `parameter`, `unit`, `value`.

### Известная ошибка в исходных данных - единицы измерения

Организаторы подтвердили: в строке единиц измерения (строка 2) есть
ошибка. В блоке **"Установка 'АВТ'. Точка отбора '1'"** единицы у
параметров `50%.T`, `EBP.T`, `D15`, `I350` сдвинуты и не соответствуют
смыслу параметра (например, `50%.T` — температура выкипания 50% фракции —
помечена как `кг/м3`).

**Как исправлено:** вместо единицы измерения из конкретной ячейки код
берет **каноническую единицу по имени параметра** — большинством голосов
по всем вхождениям этого параметра в файле. Для `I350` ничья 1:1 между
`°С` и `% об.` — разрешена вручную в пользу `% об.` (по аналогии с `I250`).

### Тест / запуск

```bash
python lims_parser.py
```
Выведет размер таблицы, первые строки, разбивку по показателям и точкам
отбора, и проверку, что у каждого параметра теперь ровно одна единица
измерения (последняя строка вывода) — так проверяется, что исправление
единиц сработало.

### Использование в коде агентов

```python
from lims_parser import parse_lims

df = parse_lims("data/ЛИМСы ... .xlsx")
```

### Другие уточнения от организаторов (не в коде, но важны при использовании)

- **Смысл `timestamp`**: момент **отбора пробы**, а не публикации
  результата. До публикации проходит **до 4 часов**. При исторической
  проверке моделей нельзя использовать результат анализа раньше, чем он
  реально мог стать известен оператору — то есть `timestamp + ~4 часа`.
- **Часовой пояс**: один и тот же для всех источников (ЛИМС, КИП, ПАК).
- **`Mg.Sulfur`** соответствует `24-2000:Mg.Sulfur` из ТЗ: Установка
  `Гидроочистка`, точка отбора `2`, продукт `Дизельное топливо`. Единица
  `мг/кг` в файле указана верно.
- **`ppm` для серы в ПАК** эквивалентен `мг/кг` — пересчет не нужен.

## pak_parser.py

Разбирает `Выгрузка_ПАК ... .xlsx`. Формат без группировки по установке/точке отбора, всего два тега — `24-2000:Mg.Sulfur` (сера, `ppm`) и `24-2000:D15` (плотность, `кг/м3`). Header — 2 строки (тег, единица), данные сразу со строки 2.

Результат — DataFrame с колонками: `timestamp`, `tag`, `unit`, `value`.

**Важно про период данных**: `Mg.Sulfur` покрывает с 2023-01-01, а `D15` —
только с **2025-03-05**. Если нужна плотность за более ранний период, в
ПАК ее нет — смотреть в ЛИМС (`D15` там тоже есть, но как периодические
лабораторные пробы).

Единицы измерения подтверждены организаторами как корректные: `ppm` для
серы эквивалентен `мг/кг` без пересчета — тот же показатель, что и
`Mg.Sulfur` в ЛИМС, только непрерывное поточное измерение вместо
периодической пробы (та же точка: `Гидроочистка`, `2`, `Дизельное топливо`).

### Тест / запуск

```bash
python pak_parser.py
```
Выведет размер таблицы, первые строки, число точек по каждому тегу и
диапазон дат по каждому — так видно расхождение периодов между `Mg.Sulfur`
и `D15`, описанное выше.

### Использование в коде агентов

```python
from pak_parser import parse_pak

df = parse_pak("data/Выгрузка_ПАК ... .xlsx")
```

## quality_formulas.py

Считает показатели качества гидроочищенного дизтоплива (`24-2000:ГОДТ`)
по формулам ВАК — но не по тем, что буквально записаны в
`Теги_хакатон.xlsx` (лист «ВАК»), а по **исправленной** версии из
переписки с организаторами: коэффициенты в T50, CloudPoint, и
делитель у F15 в T90.

Реализованы все 8 показателей `24-2000:ГОДТ` с листа «ВАК»: T90, T50,
I250, IBP, CloudPoint, CFPP — считаются напрямую по тегам КИП; T95 и
D15 — дополнительно требуют значение с точки отбора ЛИМС "Pipeline"
(см. ниже).

Не парсит файл сам — принимает на вход **один снимок тегов** (например,
одну строку из `242000_tags.csv`) и считает по нему величины.

### T95 и D15 — точка "Pipeline"

Обе формулы ссылаются на `LIMS:24-2000.Pipeline.*` — организаторы
подтвердили: "Pipeline" = точка отбора **"Гидроочистка:1"** в файле
ЛИМС (сырье на входе в гидроочистку, продукт "ФРАКЦ_ДИЗ"), не отдельный
источник.

`attach_pipeline_lims(tags_df, lims_df, parameter, ...)` делает join
тегов с этой точкой по ближайшему времени, с учетом задержки публикации
ЛИМС до 4 часов (значение считается известным не раньше
`timestamp + 4ч`).


### Тест / запуск

```bash
python quality_formulas.py
```
Читает `data/242000_tags.csv` и `data/ЛИМСы 01.01.2023 - н.в_ (2).xlsx`
(оба файла должны быть в `data/`, иначе упадёт с ошибкой на этапе join
с ЛИМС), считает все 8 показателей качества, печатает сводную
статистику, долю `NaN`/выбросов по T90, T95, D15, и сохраняет
объединенную таблицу (теги + все показатели) в `data/tags_with_quality.csv`.

### Известная проблема в данных — деление на ноль в T90

В части строк `242000_tags.csv` тег `F26` равен `0`, а формула T90 делит
на него (`-424.72638 * F1 / F26`) — без защиты это роняло бы расчет
`ZeroDivisionError`. Сейчас `compute_t90` возвращает `NaN` для таких
строк вместо падения (391 строка, 0.21%). Еще 634 строки (0.34%) дают
физически невозможный T90 при `F26`, близком к нулю, но не равном ему —
это не `NaN`, а просто выброс, отдельно не отфильтрован.

### Использование в коде агентов

```python
from quality_formulas import AvtGodtTags, compute_all, attach_pipeline_lims
from lims_parser import parse_lims

# Без ЛИМС — только 6 показателей
tags = AvtGodtTags.from_row(row)
quality = compute_all(tags)
# quality = {"T90": ..., "T50": ..., "I250": ..., "IBP": ..., "CloudPoint": ..., "CFPP": ...}

# С ЛИМС — все 8, включая T95/D15
lims_df = parse_lims("data/ЛИМСы ... .xlsx")
t95_values = attach_pipeline_lims(tags_df, lims_df, parameter="95%.T")
d15_values = attach_pipeline_lims(tags_df, lims_df, parameter="D15")
quality = compute_all(tags, lims_95pct_t_pipeline=t95, lims_d15_pipeline=d15)
```
## all_data.py

Скрипт объдинения данных тегов АВТ, Гидроочистка, ПАК и ВАК. В процессе работы запускает `quality_formulas.py`, поэтому для корректной работы необходимо чтобы имелись файлы, от которых зависит `quality_formulas.py`

Для работоспособности необходимо чтобы в директории data/ находились файлы

- avt_tags.csv
- Выгрузка ПАК 01.01.2023 - н.в_.xlsx
- файлы для корректной работы quality_formulas.py

Результат работы: файл `data/output.csv`

### Запуск

Windows:

```PowerShell
python all_data.py
```

Linux:

```Bash
python3 all_data.py
```
